# Qua wire protocol (x402-compatible)

This is the integration contract: what bytes go on the wire when a client pays
for a request. If you can speak this protocol you can integrate without the
SDK.

The protocol is `x402` ("HTTP 402 Payment Required", revived) with the
"exact" scheme and EIP-3009 USDC authorizations as the payment primitive.
Everything here is publicly described; nothing in this document leaks
operational details of the hosted facilitator.

---

## 1. The challenge: HTTP 402

When a client hits a protected endpoint without payment, your server returns:

```http
HTTP/1.1 402 Payment Required
Content-Type: application/json

{
  "x402Version": 1,
  "accepts": [
    {
      "scheme": "exact",
      "network": "base",
      "maxAmountRequired": "1000",
      "resource": "https://api.example.com/search",
      "description": "AI-powered search",
      "mimeType": "application/json",
      "payTo": "0xYourPayoutAddress",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USD Coin", "version": "2" },
      "fee": {
        "recipient": "0xPlatformFeeAddress",
        "bps": 100,
        "amount": "10"
      }
    }
  ]
}
```

Important: `maxAmountRequired` is the **gross** price the payer pays. When a
platform fee is advertised, the facilitator carves it out — the developer
receives `gross - fee.amount`. The payer never pays above the sticker price.

If `fee` is absent or `fee.amount == "0"`, this is the legacy single-leg
flow: the full `maxAmountRequired` goes to `payTo`.

## 2. The payment: X-PAYMENT header

The client signs one or two EIP-3009 `TransferWithAuthorization` messages
and base64-encodes a JSON envelope into the `X-PAYMENT` header.

The envelope:

```json
{
  "x402Version": 1,
  "scheme": "exact",
  "network": "base",
  "payload": {
    "from": "0xPayer",
    "to": "0xYourPayoutAddress",
    "value": "990",
    "validAfter": "0",
    "validBefore": "1700000060",
    "nonce": "0x<32 bytes hex>",
    "v": "0x1c",
    "r": "0x<32 bytes hex>",
    "s": "0x<32 bytes hex>"
  },
  "feeAuthorization": {
    "to": "0xPlatformFeeAddress",
    "value": "10",
    "validAfter": "0",
    "validBefore": "1700000060",
    "nonce": "0x<32 bytes hex>",
    "v": "0x1c",
    "r": "0x<32 bytes hex>",
    "s": "0x<32 bytes hex>"
  },
  "feeSignature": "0x<copied into feeAuthorization above for older verifiers>"
}
```

The two signed legs sum to `maxAmountRequired`. The developer leg (`payload`)
pays `gross - fee.amount` to the developer; the fee leg (`feeAuthorization`)
pays `fee.amount` to the platform.

Encode the JSON, base64 it (**standard** alphabet, with padding — not
URL-safe), and send as `X-PAYMENT: <base64>`.

## 3. The response: X-PAYMENT-RESPONSE header

On success the server returns 200 with a base64-encoded settlement receipt
in `X-PAYMENT-RESPONSE`:

```json
{
  "success": true,
  "network": "base",
  "transaction": "0x<net leg tx hash>",
  "feeTransaction": "0x<fee leg tx hash, omitted if no platform fee>",
  "payer": "0xPayer",
  "asset": "0x...USDC...",
  "amount": "990",
  "fee": "10"
}
```

`amount` is the **net** delivered to the developer (`gross - fee`). `fee` is
the platform fee. Sum them to recover the gross.

## 4. Failure modes

- `402 Payment Required` with `error: "payment verification rejected"` — the
  X-PAYMENT signature was invalid, the validity window expired, the payer
  address mismatched, the asset/network didn't match the requirements, or
  the payer is unwilling to authorize the gross amount. Sign a fresh
  payment and retry.
- `502 Bad Gateway` with `payment verification failed: …` — the verifier
  could not reach the upstream RPC. Transient; retry.
- `502 Bad Gateway` with `settlement failed: …` — verify passed but on-chain
  submission failed. Often relayer-side (gas, RPC blip). Treat as transient
  and retry with the same signed authorization (idempotency by nonce).
- `403 Forbidden` with `payTo does not match the developer's registered
  payout address` — the request specified a `payTo` other than the one the
  developer has pinned. By default the facilitator refuses to settle
  unpinned payout addresses; this is intentional, to bound the blast radius
  of a stolen API key.

## 5. Idempotency

The facilitator uniquely indexes each settlement by
`(network, payer, nonce)`. A retry with the same signed authorization
returns the original receipt; the on-chain transfer fires exactly once.
This is the safe retry primitive: pick a fresh nonce per new payment, reuse
the same nonce when you want to retry.

## 6. Routes (control API, brief)

To pin your payout address and configure pricing, the Control API exposes:

- `POST /v1/routes` — create a route with a path + price + payTo.
- `GET /v1/routes` — list your routes.
- `POST /v1/keys` — mint a new developer API key.
- `GET /v1/keys` — list your API keys.

All Control API calls are Bearer-authenticated with your `ap_live_…` key.

## 7. Networks supported

- `base` (production, chain ID 8453)
- `base-sepolia` (testnet, chain ID 84532)

Other networks may be added; the canonical list is whatever
`https://facilitator.qua.run/v1/health` advertises in its
`supported_networks` field.

## 8. Versioning

`x402Version` is currently `1`. Breaking changes bump the version; old
versions keep working for a deprecation window (announced via the status
page).

---

That's the entire protocol. If you can produce a base64-encoded
`X-PAYMENT` header that the facilitator accepts, you've integrated.
